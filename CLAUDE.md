# Engineering Rules

Treat this as a production project that a senior developer will review. Aim for
clean, maintainable, top-tier code (Linear / Vercel / Stripe quality bar). When
something would not pass senior review, do not ship it.

## Git workflow

- Never commit directly to `main`.
- One shared development branch: `Feranmibranches`. All work, from any
  session (scheduled or live), commits and pushes there. Do not create a new
  branch per task or per fix; too many branches is the problem this replaces.
  Open a PR from `Feranmibranches` into `main` for the owner to review and
  merge themselves; do not merge it yourself.
- Do not add AI or assistant attribution, "Generated by AI", "Co-Authored-By",
  or any Claude/assistant credit to commits, PRs, comments, or code.
- No unnecessary commits. Commit meaningful, complete units of work with clear
  messages.
- Avoid em dashes in commit messages, PRs, code, comments, and docs. Use plain
  punctuation (commas, colons, periods).
- Commit and push only when asked. Open PRs for the owner to merge themselves
  unless told otherwise.

## Code quality

- Strong typing everywhere. Never use `any`. Prefer precise types, generics, and
  inferred types.
- No dead code, no commented-out blocks, no leftover TODOs without context.
- Match the surrounding code: naming, comment density, and idioms. New code
  should read like it was already there.
- Comment only where it adds real value (the "why", not the "what").
- Follow the locked stack. Do not introduce a new library when an approved one
  already covers the need. Confirm before adding dependencies.
- Validate inputs at boundaries with a schema library (Zod). Keep data flow
  typed end to end.

## Architecture and components

- A file must not exceed roughly 200 lines. If it grows past that, split it into
  smaller components or modules.
- One responsibility per file or component. Extract reusable primitives instead
  of duplicating.
- Keep features self-contained and loosely coupled. Separate concerns (UI,
  state, data, validation).
- Design tokens and theme values live in one place. Components reference semantic
  tokens, not hardcoded values, so retheming means editing tokens, not
  components.
- Keep unrelated areas of code independent. Do not entangle things that should
  stay separate.

## Design and UI

Follow [docs/ui.md](docs/ui.md) and [docs/color.md](docs/color.md) as the design
source of truth. Design tokens are defined once in `apps/web/src/app/globals.css`.

- Clean, minimal, premium. No AI-generated look, no clutter.
- Do not fabricate images, mockups, logos, or screenshots. If an asset is
  needed, ask for it.
- Accessibility is a requirement, not an afterthought: proper labels, focus
  states, keyboard support, adequate hit targets and contrast.
- Care about performance: avoid unnecessary re-renders, lazy-load where it
  helps, keep bundles lean.
- Responsive and theme-aware (light and dark) where relevant.

## Local development

- Do not run `pnpm dev` in a way that shells out to an unfiltered
  `turbo run dev` at the repo root, and do not run `turbo run dev` directly.
  Turbo starts every workspace dev server at once, and several cold-starting
  bundlers compiling together can pin CPU and RAM and freeze the machine.
- Start the stack with [`dev.sh`](dev.sh) (`pnpm dev` runs it). It starts a
  curated set of services one at a time, waits for each to be ready, writes
  per-service logs to `.dev-logs/`, and tears down cleanly on Ctrl+C.
- Turbo stays the task runner for `build`, `lint`, and `typecheck`, which are
  safe to fan out.

## Verification and honesty

- Verify changes actually work before claiming they are done. Run the type
  checker, the build, and the app; check the real output.
- Never ask for manual verification of something that can be checked directly.
  Check it and show the proof.
- Report outcomes faithfully. If tests fail, say so with the output. If a step
  was skipped, say that. State clearly when something is done and verified,
  without hedging or overclaiming.
- Flag speculative or risky changes explicitly rather than burying them.

## Working style

- When there is enough to act, act. Do not re-litigate settled decisions or
  narrate options that will not be taken.
- When a choice is genuinely the owner's and irreversible (deleting branches or
  data, rewriting shared history, destructive migrations), confirm the exact
  plan before executing.
- Give a recommendation, not an exhaustive survey, when weighing options.
