# Telegram engineering agent (V1)

Control this repository's Claude engineering workflow from Telegram.

```
Telegram → Vercel (Python serverless) → GitHub API (repository_dispatch)
  → GitHub Actions → Claude Code (claude-code-action) → repo (branch/PR)
  → GitHub Actions → Vercel (signed callback) → Telegram
```

## Why this authenticates the way it does

This repository has **no existing GitHub Actions workflow that runs Claude**
(checked `.github/workflows/ci.yml`, `database.yml`, `edge-functions.yml`,
`security.yml` — none of them touch Claude). The actual "existing Claude
engineering workflow" for this project is a separate system: scheduled
Claude Code Cloud sessions (see `docs/loop-engineering/`), which are not
reachable from outside via any GitHub API and cannot be the target of a
`repository_dispatch`.

So `.github/workflows/telegram-claude-task.yml` is new. It authenticates
Claude the same way your Claude Code CLI does — an OAuth token tied to your
Claude subscription (`CLAUDE_CODE_OAUTH_TOKEN`, generated by running
`claude setup-token` locally), via the official
[`anthropics/claude-code-action`](https://github.com/anthropics/claude-code-action).
This is **not** a pay-per-token `ANTHROPIC_API_KEY` — it's the same OAuth
credential your existing Claude Code setup already uses.

## How state works (there is no database)

- **Which chat to notify**: never looked up. The Vercel backend puts
  `telegram_chat_id` in the `repository_dispatch` payload; the workflow
  echoes it straight back in its callback. Zero storage needed.
- **Follow-up messages**: every bot message about a task ends with a
  monospaced footer, e.g. `` `task_20260828_abc123 session:sess-1
branch:claude/telegram-abc123` ``. Reply to that message in Telegram
  ("Now add a regression test") and the webhook parses the footer out of
  `message.reply_to_message.text`, re-dispatches with `resume_session_id`
  (so `claude-code-action` resumes the same session via `--resume`) and
  `base_branch` (so the workflow checks out the existing branch instead of
  the default branch). No database, fully stateless.
- **`/status` and `/cancel`**: query the GitHub Actions API live for the
  telegram-claude-task workflow's recent runs, rather than tracking
  anything locally.
- **Idempotency**: handlers respond to Telegram within a couple of seconds
  (a single outbound HTTP call), which is what stops Telegram from
  retrying a delivery. There's no dedup store beyond that; a genuine retry
  after a slow/failed response could in principle create a second
  `repository_dispatch`. Acceptable for V1 given how rare that is; a real
  fix (an idempotency key keyed on Telegram's own `update_id`) needs a KV
  store — see "Evolving past V1" below.

## Project layout

```
services/telegram-agent/
  api/
    health.py              GET  /api/health
    telegram/webhook.py    POST /api/telegram/webhook
    github/callback.py     POST /api/github/callback
  lib/
    config.py               env var loading/validation
    security.py              allowlist + signature checks
    tasks.py                 task ids, footer encode/decode
    messages.py              Telegram message templates
    commands.py               /start /help /status /cancel + task dispatch
    telegram_client.py        Telegram Bot API
    github_client.py          repository_dispatch, list/cancel runs
    http_utils.py              BaseHTTPRequestHandler read/write helpers
  tests/                       unit tests (no network, no credentials needed)
  requirements.txt
  vercel.json
  .env.example
```

Each `api/*.py` file uses Vercel's file-based Python routing: a
`BaseHTTPRequestHandler` subclass named `handler`, one function per HTTP
method. `api/telegram/webhook.py` maps to `/api/telegram/webhook`.

## Environment variables

See `.env.example`. All of these are **Vercel project environment
variables** (Settings → Environment Variables), not GitHub secrets:

| Variable                    | Purpose                                                                                                  |
| --------------------------- | -------------------------------------------------------------------------------------------------------- |
| `TELEGRAM_BOT_TOKEN`        | From [@BotFather](https://t.me/BotFather)                                                                |
| `TELEGRAM_ALLOWED_USER_IDS` | Comma-separated numeric Telegram user IDs. Get yours from [@userinfobot](https://t.me/userinfobot)       |
| `TELEGRAM_WEBHOOK_SECRET`   | Any random string you generate (`openssl rand -hex 32`); registered with Telegram as `secret_token`      |
| `GITHUB_TOKEN`              | A token (fine-grained PAT recommended) with Contents, Pull requests, and Actions read/write on this repo |
| `GITHUB_OWNER`              | `ferousco-dev`                                                                                           |
| `GITHUB_REPOSITORY`         | `beyond-social`                                                                                          |
| `GITHUB_WORKFLOW_FILE`      | `telegram-claude-task.yml` (default)                                                                     |
| `GITHUB_WEBHOOK_SECRET`     | Random string (`openssl rand -hex 32`); **must match** the GitHub Actions secret of the same name below  |

### GitHub Actions secrets (repo Settings → Secrets and variables → Actions)

These are separate from the Vercel env vars above:

| Secret                    | Purpose                                            |
| ------------------------- | -------------------------------------------------- |
| `CLAUDE_CODE_OAUTH_TOKEN` | Output of `claude setup-token` (Claude Pro/Max)    |
| `TELEGRAM_CALLBACK_URL`   | `https://<your-vercel-domain>/api/github/callback` |
| `GITHUB_WEBHOOK_SECRET`   | Same value as the Vercel env var above             |

## Deploy

```sh
cd services/telegram-agent
vercel deploy --prod
```

(Not run by this change — see "What still needs your action" below.)

## Register the Telegram webhook

Once deployed, point Telegram at it:

```sh
curl -X POST "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://<your-vercel-domain>/api/telegram/webhook",
    "secret_token": "<TELEGRAM_WEBHOOK_SECRET>"
  }'
```

Verify it took:

```sh
curl "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/getWebhookInfo"
```

## Running the tests

No credentials needed; the suite covers the allowlist, signature
verification, and the task-footer round trip:

```sh
cd services/telegram-agent
pip install -r requirements.txt
PYTHONPATH=. python3 -m unittest discover -s tests -v
```

## Safety

- Telegram messages become the `prompt` input to `claude-code-action`.
  There is no `/exec` or `/shell` command anywhere in this system — every
  message is a high-level instruction to Claude, which then operates
  within the permissions already granted to the workflow's `GITHUB_TOKEN`
  (`contents: write`, `pull-requests: write`, `issues: write` — nothing
  broader). Nothing here auto-merges to `main`.
- Only the Telegram user IDs in `TELEGRAM_ALLOWED_USER_IDS` can trigger
  anything; everyone else gets a generic "⛔ Unauthorized." with no detail.
- Both webhook endpoints are signature-checked (Telegram's own
  `secret_token` mechanism; a bespoke HMAC-SHA256 for the GitHub→Vercel
  callback, since that's a plain POST from a workflow step, not a native
  GitHub webhook).
- No secret is ever logged; failures log only the HTTP status/exception
  type.

## Evolving past V1

The reply-to-message follow-up mechanism and the live GitHub Actions
queries for `/status`/`/cancel` are the seams designed to be replaced with
real storage later without a rewrite: `lib/tasks.py` isolates task-identity
handling, and `lib/github_client.py` isolates every GitHub API call. Adding
a KV store later means changing those two files, not the handlers.
